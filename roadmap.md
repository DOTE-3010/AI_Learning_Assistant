# Solver#42 Development Journey

This document records how the Solver#42 Local MVP was transformed step-by-step from a concept into the final deliverable. We adopted an **"Inside-Out"** development strategy, prioritizing core business logic first and wrapping it with the interface and deployment tools last.

---

## 🚀 Phase 1: Core Engine Construction

**Goal**: Verify if the LLM can generate high-quality answers based on questions and search results.

In this phase, we ignored the Web interface and database entirely, writing only pure Python scripts.
1. **LLM Client Encapsulation**:
   - Wrapped the `Bianxie` interface based on the `openai` SDK.
   - Implemented the `StandardAnswerGenerator` class to handle Prompt Engineering.
2. **Web Search Integration**:
   - Introduced the `duckduckgo_search` library.
   - Implemented `perform_web_search` to automatically convert questions into queries and inject cleaned Top-3 results into the System Prompt.
3. **Multi-Format Output Protocol**:
   - Defined internal conversion logic to transform plain text LLM responses into `.py` code blocks, `.ipynb` JSON structures, or `.md` documents.

**Deliverables**: `backend/app/standard_answer_generator.py` and CLI test scripts.

---

## 💾 Phase 2: Hybrid Data Layer Design

**Goal**: Implement data persistence and define the storage strategy for "Metadata" vs "Documents".

To balance structured queries and unstructured content, we designed a dual-database architecture:
1. **PostgreSQL (Docker)**:
   - Defined `User`, `Course`, `Assignment`, `GenerationJob` table structures.
   - Used `SQLAlchemy` as the ORM.
   - Solved user relationship and task status tracking.
2. **MongoDB (Docker)**:
   - Created the `artifacts` collection.
   - Used for storing large text blocks, JSON, and logs generated by the LLM to avoid bloating SQL tables.
3. **Local Filesystem (Workspace)**:
   - Implemented logic for `save_local_file`.
   - Established the `workspace/{Course}/{Assignment}/solution_{timestamp}.{ext}` directory standard to ensure users can directly access files.

**Deliverables**: `backend/app/database.py`, `backend/models/`, and `docker-compose.yml`.

---

## 🔌 Phase 3: API Service

**Goal**: Transform Python scripts into a RESTful API accessible via HTTP.

1. **FastAPI Framework Setup**:
   - Initialized the `FastAPI` application and configured CORS.
2. **Auth Middleware**:
   - Developed `email_auth_middleware`.
   - Implemented a **Zero-Config RBAC** permission system based on email suffixes (`@cuhk.edu.hk`).
3. **Async Task Queue**:
   - Utilized FastAPI's `BackgroundTasks` to offload generation tasks from the main thread.
   - Designed a `queued` -> `running` -> `succeeded` state machine paired with frontend polling.
4. **File Upload Handling**:
   - Implemented `UploadFile` processing logic to support passing uploaded file content as additional context to the LLM.

**Deliverables**: `backend/main.py`.

---

## 🎨 Phase 4: Frontend & UX

**Goal**: Provide a modern, intuitive user interface.

1. **Static Resource Integration**:
   - Decided against using extra frontend build tools (like Webpack), opting for native HTML/JS.
   - Embedded the frontend directly into the backend service via `app.mount("/ui", ...)`.
2. **UI Design**:
   - Adopted a "Glassmorphism" style adapted for dark mode.
   - Designed a layout with Left Navigation + Right Chat Box.
3. **Interaction Logic**:
   - Implemented no-refresh `fetch` requests.
   - Wrote polling logic: Click Generate -> Receive Job ID -> Query Status every second -> Render Result.

**Deliverables**: `backend/static/index.html`.

---

## 📦 Phase 5: Local Packaging

**Goal**: Enable non-technical users to launch the system with one click.

This was the "Last Mile" of the MVP.
1. **Port Conflict Prevention**:
   - Locked the backend port to `14242` and Postgres to `15432` to avoid common conflicts on `8000` and `5432`.
2. **Startup Scripts**:
   - Wrote `start_mvp.command` (Shell) and `demo_launcher.py` (Python).
   - Script Logic:
     1. Check and start Docker Desktop.
     2. Run `docker-compose up -d` to start databases.
     3. Create Python virtual environment and install `requirements.txt`.
     4. Start the `uvicorn` server.
     5. Automatically open the browser to `http://localhost:14242`.
3. **Persistence Verification**:
   - Verified that Docker Volumes and Local Workspace data persist after computer restarts.

**Final Deliverable**: A complete, self-contained local application package.

---

## 🏆 Summary

Through these five phases, we built a fully functional Generative AI application from scratch without relying on external cloud services. This process proved the efficiency and practicality of the **Local Hybrid Architecture** for educational scenarios.
